## 德鲁克语言地图

| 组织语言 | 适合承接的问题 | 行动化方向 | 常见误用 |
|---|---|---|---|
| 使命与外部成果 | 组织为何存在、结果在哪里发生 | 明确服务对象、价值、取舍和可验证结果 | 用口号或活动代替外部成果 |
| 顾客与价值 | 顾客是谁、为何选择、何谓有价值 | 观察选择、购买、使用、留存与问题解决 | 由内部替顾客定义价值 |
| 有效性与贡献 | 是否在做对的事、角色应贡献什么 | 把活动指标转成成果与贡献 | 把忙碌、会议或培训完成率当绩效 |
| 目标与自我控制 | 如何让共同方向转成自主负责 | 同时下沉目标、责任、决策权与反馈信息 | 把 MBO 简化成上级压数字或 KPI 堆叠 |
| 发挥长处 | 如何让人的优势产生绩效 | 岗位配置、互补协作与反馈分析 | 用“发挥长处”纵容伤害组织的行为 |
| 创新与有计划地放弃 | 如何为未来释放资源 | 形成停止清单、重配资源、验证新价值 | 把新品、技术采购或变化都称为创新 |
| 分权与责任 | 如何兼顾自治与共同成果 | 按成果单元配置权责，保留方向与衡量 | 把分权理解成无标准、无问责 |
| 管理责任与人的发展 | 如何兼顾绩效、判断力与尊严 | 让人获得信息、能力、责任与成长机会 | 用“以人为本”回避绩效和艰难取舍 |

德鲁克语言主要校验“做什么、为何做、为谁创造什么成果、谁对什么负责”。它不能替代：

- 当前市场、法规、客户和竞争证据；
- 现场流程与质量技术分析；
- 财务、法律、安全或统计验证；
- 外部方法自身的独特因果机制。

## TPS 语言地图

| 组织语言 | 适合承接的问题 | 行动化方向 | 常见误用 |
|---|---|---|---|
| 顾客需要、质量、成本与及时交付 | 流程输出是否满足真实需要 | 从顾客需求反推交付条件和价值流 | 只谈内部效率，不看顾客与质量 |
| 现地现物 | 判断是否脱离现场、事实是否可见 | 观察人、物、信息、等待和异常 | 把巡视或参观当作调查完成 |
| 自働化（Jidoka） | 异常如何被发现、停止并防止流出 | 定义异常、停线/暂停权、响应与防复发 | 误写成单纯自动化；惩罚暴露问题的人 |
| 准时化（Just-in-Time） | 是否按真实需求形成连续流动 | 需要的时间、数量、节拍、拉动和同步 | 把零库存或局部满负荷当目标 |
| 流动与拉动 | 工作是否排队、批量化或跨接口停滞 | 缩短等待与切换，由下游需求触发 | 局部提速造成下游堆积 |
| Muda / Mura / Muri | 浪费、波动和过载如何损害系统 | 同时观察非增值、负荷不均与人机过载 | 只裁人降本，或把必要缓冲全算浪费 |
| 标准作业 | 当前最佳已知方法是否可重复、可比较 | 定义基线、关键步骤、条件和异常 | 把标准固化成不可挑战的命令 |
| 改善（Kaizen） | 如何让问题转成持续学习 | 小步试验、现场参与、前后比较、更新标准 | 只统计建议数，或让改善成为额外负担 |
| 可视化与安灯 | 状态、异常和响应责任是否及时可见 | 定义正常/异常、响应人和升级条件 | 用大屏替代真实响应机制 |
| 尊重人、让工作更容易 | 改善是否释放人的判断与价值 | 消除无意义负担，让一线能停、报、改 | 用“精益”持续压人、压安全余量 |

TPS 官方核心以 Just-in-Time 与 Jidoka 为基线。A3、价值流图和后来的 Lean 工具可能与 Toyota 有直接或间接关系，但不能因此全部称为“TPS原生支柱”。

TPS 主要校验“工作如何流动、异常如何暴露、质量如何内建、改善如何持续”。它不能自动回答：

- 企业使命、业务边界和战略取舍；
- 顾客细分、市场吸引力和资源组合；
- 所有组织政治、激励或个人行为问题；
- 外部方法所需的统计、技术或行业证据。

## 双体系分工

优先择一；只有跨层互补成立时才组合：

| 问题层次 | 主语言 | 另一体系可补充 |
|---|---|---|
| 企业目的、顾客定义、成果和取舍 | 德鲁克 | TPS 检查交付系统是否支持顾客成果 |
| 角色贡献、责任、决策权和自我控制 | 德鲁克 | TPS 把异常、信息和反馈嵌入日常工作 |
| 流程、交期、在制、质量和异常 | TPS | 德鲁克校验改善是否服务外部成果 |
| 现场学习、标准与持续改善 | TPS | 德鲁克校验人的发展、贡献和责任 |
| 战略到执行 | 德鲁克界定成果、取舍和责任 | TPS 设计流动、节拍、异常与改善机制 |

两套语言出现分歧时，不投票、不平均。先判断事实、假设、层级、时间跨度和价值取向差异，再决定由证据验证还是由负责人取舍。

## 主干式叙事

“主干”描述当前方案采用什么经营判断和执行约束，不描述外部方法的历史来源：

- **德鲁克作为经营主干**：界定顾客、外部成果、资源取舍、贡献和责任。
- **TPS作为执行主干**：把已经确认的要求转成现场标准、质量内建、流动、异常响应和改善。
- **外部方法作为专业工具**：承担描述、诊断、生成、评估、反证或研究任务。

只有实际完成相应校验后，才说“经营上遵循德鲁克、执行上由 TPS 承接”。若一套体系不适用，明确其退出或后续介入点；不要为了企业偏好制造弱关联。

独立方法的基本表达：

> 本方案在经营判断上遵循德鲁克的[原则]，在执行上由 TPS 的[机制]承接；[外部方法]负责帮助识别或验证[具体问题]。

只有德鲁克校验和 TPS 机制都已实际成立时才可完整使用该句。TPS 只处于候选承接时，必须改为“满足[缺失条件]后可由TPS承接”；TPS 不直接适用时删除TPS半句。任何情况都不能改写为“外部方法源自德鲁克/TPS”。

## 桥接成立条件

| 外部结论 | 可以连接的条件 | 不成立时的表达 | 禁止偷换 |
|---|---|---|---|
| 顾客说某功能重要或属于Kano基本型 | 已通过有效研究确认，并被负责人采纳为产品/服务质量要求 | 顾客研究提示的基本要求，待确认是否进入质量标准 | 直接称为TPS质量异常或缺陷 |
| 产品/项目投入过多 | 有证据显示活动不创造所需价值、造成排队、返工或超过真实需求 | 待验证的非增值投入或资源错配 | 直接称为TPS“过量生产” |
| 顾客满意度变化 | 有行为、交易或持续使用证据支持其经营含义 | 满意度信号或研究假设 | 等同购买、留存、支付意愿或利润 |
| 个体心理或行为机制 | 已进入具体工作流程、工作标准或异常响应 | 个人/顾客层的诊断，对TPS不直接适用 | 用“尊重人”把任何心理理论接成TPS |
| A/B测试、受控实验或一般小步试验 | 另用实验设计、PDSA或统计方法形成可比较证据；TPS只检查实际交付流程 | 实验方法负责验证假设，TPS待进入交付后介入 | 把“有标准、有反馈、会改善”直接等同TPS |
| 外部方法提出行动 | 德鲁克已校验顾客成果与责任，TPS已校验具体执行接口 | 外部方法建议，仍待经营和执行校验 | 称为德鲁克/TPS原生行动 |
| 方法使用相似术语 | 一手资料证明历史影响，或当前机制满足明确桥接条件 | 语义相似或执行衔接 | 从相似词推导血缘 |

## 标签与归因话术

为防止弱模型把任务模式、证据等级和备选方案混在一起，只使用：

- **任务模式**：`M-A1 / M-A2 / M-B / M-C`。
- **证据等级**：`E-A / E-B / E-C / E-D`。
- **备选方案**：写“方案一/方案二”或真实方案名称，禁止写“A/B”。

当审核对象是独立方法或谱系未证实时，M-C 归因审核使用固定结构：

> [外部方法]是独立方法；本方案在经营判断上用德鲁克的[具体原则]校验，进入[真实流程]并建立[标准、异常信号、责任权限]后，再由TPS校验[具体接口]，不能称其源自TPS。

文化适配只有三档：

| 证据状态 | 允许表达 |
|---|---|
| 历史谱系有可靠证据 | “源自/后生发展/明确受影响”，并附证据 |
| 当前经营校验成立 | “经营上经过德鲁克的[具体原则]校验” |
| TPS接口已成立/尚待建立 | 分别说“由TPS的[具体机制]承接”/“满足[条件]后可由TPS承接” |

禁止用“共同管理主线”“质量关卡”“TPS思想延伸”等含混表达替代谱系和机制证据。

## TPS关系状态

先判断状态，再选择术语。必须且只能在“已成立、候选承接、不直接适用”中选一个，不得用斜杠或“同时”组合状态。不要从“像不像TPS”直接跳到“由TPS承接”。

| 状态 | 最低证据 | 允许表达 | 禁止表达 |
|---|---|---|---|
| 已成立 | 真实流程 + 标准或需求信号 + 可观察异常或流动规则 + 响应责任/权限 | “由TPS的[具体机制]承接” | 缺少其中任一条件时仍称已落地 |
| 候选承接 | 已识别具体流程接口，但标准、信号、异常、责任或权限尚缺 | “若建立[缺失条件]，后续可由TPS承接” | “已经用安灯/拉动/标准作业解决” |
| 不直接适用 | 当前对象主要是战略、顾客研究、个人心理或其他非流程问题 | “TPS待进入真实交付流程后再评估” | 用尊重人、改善、反馈等宽泛词硬接 |

已有 UF/EF 同时支持真实流程、标准/需求信号、异常/流动规则和响应责任/权限时，必须选“已成立”；不能因机制仍可改善而降级为候选。

### 具体术语的必要条件

- **安灯/自働化/拉停**：必须同时存在正常标准、异常信号、停止或呼叫动作、明确响应角色。网站流失、满意度下降、需求不清等现象本身不是安灯。
- **准时化/拉动/流动**：必须存在真实需求信号、明确工作单元，以及在制品、补充或节奏规则。等待或瓶颈本身不足以证明TPS流动机制已建立。
- **标准作业**：必须是可执行、可观察且可更新的既定最佳方法。Agent提出“把它标准化”只是建议，不是现有标准作业。
- **异常**：必须相对于已经确认的正常状态或质量要求。没有标准时只能称问题信号或待诊断差距。

技术容量、系统并发数、告警和仪表盘只是事实条件：容量或并发数只有在实际控制工作进入、排队、补充或节奏时，才可能构成在制/流动规则；告警或仪表盘只有连接到正常标准、异常动作和响应责任时，才可能构成安灯接口。不得从技术参数或可视化界面直接推导 TPS 已成立。

继续执行以下分离：

- 来源置信度只回答“来源是否可靠”，不回答“与德鲁克/TPS有多接近”。
- 方法谱系只回答“历史上从哪里来”，不回答“当前能否衔接执行”。
- 顾客偏好、满意度、选择、购买、留存和支付意愿分别取证。
- 建议角色与已确认负责人分别标注；不能把“通常由CPO负责”写成组织事实。
- 质量要求、设计选择和流程异常分别判断；不能因顾客不满意自动启动 Jidoka 话术。
- 实验学习和TPS改善分别判断；不能把任何“小步试验”都称为TPS。

## 常见语义碰撞

| 看似相近 | 必须保留的差异 |
|---|---|
| OODA 与 PDCA/PDSA | OODA强调对抗和不确定性中的定向与行动；PDSA强调预测、试验和学习 |
| 沃德利地图与价值流图 | 前者描述用户需要、组件依赖与演化；后者描述物料/信息流、等待与未来状态 |
| 知识工作 Kanban 与丰田看板 | 前者是服务流管理方法；后者是支撑 JIT 的生产信号机制 |
| OKR 与 MBO | OKR有自身格式和运行历史；不能因目标、反馈相似就称为德鲁克原生 |
| Lean、TPS 与精益创业 | TPS是特定生产体系；Lean及精益创业有不同传播史、对象和机制 |
| A3 与 TPS核心 | A3与 Toyota 实践有直接关联，但不等同 Just-in-Time/Jidoka 两大支柱 |
| TOC 与 TPS | TOC以系统约束和吞吐为核心；TPS同时处理流动、质量、异常、波动与过载 |
| COM-B 与尊重人/自我控制 | 作业环境可互补，但操控行为或绕过自主责任时存在价值冲突 |
| Stage-Gate Gate 与 Jidoka 异常停止 | 前者是创新项目的阶段投资/治理决策；后者是真实交付流程中对质量异常的发现、停止和响应，不能因都有“停/继续”就视为同一机制 |

出现这些组合时，强制进入方法核验；不能只靠词义类比。

## 不可翻译与冲突处理

- 原方法包含德鲁克/TPS未覆盖的机制时，保留外部术语并说明其新增价值。
- 层级错配时，不寻找相似词；明确“该体系不直接回答此问题”。
- 价值冲突时，说明相似点和张力，提出约束或替代方案。
- 完整方法与局部组件分别判断；局部 E-A/E-B 不能自动升级整个方法。
- 只有可靠来源能证明历史影响时，才使用“由……发展”“受……影响”。
