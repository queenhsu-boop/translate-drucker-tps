# 输入整理与老板汇报

用于口头转录、零散笔记、会议纪要、半成品方案和老板汇报。目标是让输入形式宽容，让事实纪律和终止行为严格。

## 重建输入

先从原材料提取：

1. 汇报对象，以及希望对方决定、批准或理解什么。
2. 经营问题、顾客或受影响对象、目标成果。
3. 已知事实、用户判断、待验证假设和缺失信息。
4. 外部方法及其本次实际职责；名称未知时只描述机制，不擅自命名。
5. 用户已经提出的计划、倾向、选择、方案、行动、责任、证据和风险。

不要要求用户按模板重写。多人观点要标明来源角色；无法识别时写“来源角色待确认”。

## 建立最小事实账本

只记录会改变结论的陈述，并拆到每项只含一个主张：

| 代码 | 类型 | 判断标准 | 可否作为前台事实 |
|---|---|---|---|
| UF | 用户事实 | 用户明确陈述的可观察事实 | 可以，必要时写“据当前输入” |
| EF | 外部事实 | 直接来源支持，且已证实适用当前案例 | 可以，后台记录来源和适用范围 |
| UJ | 用户判断 | 用户/团队已有的解释、计划、倾向、选择、方案或建议 | 只能写“当前判断/团队倾向” |
| AI | Agent推断 | Agent 根据证据新形成的解释 | 必须附依据与可推翻条件 |
| AS | Agent建议 | 只指 Agent 新增的行动或参数 | 必须写“建议”，不得伪装成已决定 |
| UK | 待确认 | 当前没有可靠来源 | 不能作为事实或确定参数 |

用户已有的计划或建议必须归入 UJ，不能因其是“建议”就标 AS。AS 只标 Agent 在本次回答中新增的行动。

### 承诺强度不可升级

前台沿用输入中的最低必要强度，不做“更像结论”的润色：

| 输入状态 | 前台允许表达 | 禁止升级 |
|---|---|---|
| 考虑、倾向、准备、建议、尚未批准 | “团队倾向/正在考虑/准备验证/建议” | 决定、既定选择、方向正确、已经安排 |
| 已决定、已批准 | “已经决定/批准” | 已开始执行、已完成、已产生结果 |
| 已开始、正在执行 | “正在执行” | 已完成、已验证有效 |
| 方法分类或诊断 | “团队通过X判断/当前诊断提示” | X证明、方向正确、应列为第一优先 |
| Agent新增动作 | “建议……” | 团队计划、组织决定、负责人已经承诺 |

如果输入同时包含较弱和较强的说法，以能回指 UF/EF 的强度为上限。计算比例、汇总数量或形成 AI 推断时，仍需说明其来源和可推翻条件。

### 强制逐项扫描

检查所有：

- 阿拉伯数字、百分比、金额、数量、日期、周期和频率。
- 人名、岗位、部门、责任分配和决策权。
- “已经、目前、一直、普遍、唯一、导致、证明”等事实或因果词。
- “标准、异常、安灯、拉停、拉动、流动”等现有机制。

每项都必须回指 UF/EF。否则删除具体值、降级为 UJ/AI/AS/UK，或在它会改变核心结论时进入阻断状态。

## 选择唯一输出状态

按顺序检查，命中后不再评估后续状态：

### 1. `ASK_ONE`

当缺失信息同时满足以下条件：

1. 至少两种核心结论都合理成立。
2. 不同结论会导致不同老板决策、方法选择或主要风险。
3. 答案必须由用户提供，不能从输入、附件或合规联网资料得到。

一个问题只能要求一个独立答案。如果两部分需要不同数据、不同人回答，或会分别改变不同决策，就是两个问题；只保留影响最大的一个。

只索取能够区分核心选择的最小答案；若“流失主要集中在哪一步”已经足够，不再要求整套漏斗、跌幅和原因同时提交。备选项使用真实名称或“方案一/方案二”，禁止写“A/B”。

唯一允许输出：

```markdown
## 需要补充的信息

[一个可独立回答的问题]

这会影响：[具体选择或风险]。
```

然后立即停止。不展示事实账本、方法边界、TPS状态、行动建议或老板汇报。

不会改变方向的负责人、目标值或周期未知时，不提问，标 UK 并继续。

### 2. `WAIT_EVIDENCE`

以下情况命中：

- 必须联网，但当前无法取得可靠来源。
- 直接来源互相冲突，且冲突会改变结论。
- 能证明一般背景，却无法证明它适用于当前企业、地区、产品或时间。
- 删除无来源的关键外部事实后，已不能支持正式结论。

唯一允许输出：

```markdown
## 已整理的信息

- 用户已给信息：
- 当前可确认的边界：
- 待确认适用项：

## 待联网核验

- 需要核验的主张：
- 需要的直接来源/适用条件：

完成核验前不生成正式老板汇报、正式结论或血缘归因。
```

然后立即停止。不得附带方法定论、老板话术、行动路线或建议方案。

### 3. `DELIVER`

只有未命中上述两个状态才能进入。此时默认输出老板前台和后台依据。

## 检查外部事实适用性

联网“找到来源”不等于“证明适用”。每项准备进入老板前台的 EF 都使用：

| 原始主张 | 直接来源/发布日期 | 来源支持的对象、地区、产品、时间 | 当前案例适用条件 | 状态 |
|---|---|---|---|---|
| | | | | 已证实适用 / 仅背景信息 / 待确认适用 |

仅“已证实适用”可作为前台事实。另两种不得支撑公司影响、方案优劣或确定归因。

强制检查：

- **关税**：同时确认 HS 编码、原产地、税率、生效时间。未确认 SKU/HS 编码时，“最高税率”只是背景信息。
- **比较结论**：“最低成本、最快、最高风险”需要同一口径、同一时点、覆盖全部备选方案的数据。否则改为“建议优先验证”。
- **政策状态**：将政治立场、征求意见/讨论方向、已通过或已生效结果分开。
- **来源级别**：二手报道可用于找线索；正式政策尽量回到政府、法规或主管机构原文。

如果前台结论必须依赖“仅背景信息/待确认适用”，回到 `WAIT_EVIDENCE`。

## 形成`DELIVER`老板前台

按以下顺序形成 150–300 个汉字的老板汇报：

1. **经营问题**：当前结果差距，不从方法或理论开始。
2. **关键证据**：一至三项 UF/已证实适用的 EF；UJ/AI 必须显式标明。
3. **判断与选择**：用户既有选择是 UJ；严格复用“考虑/倾向/决定/执行”等原始强度。Agent 新增行动才是 AS；外部方法完成分类不等于证明优先级正确。
4. **管理主干**：只点名实际适用的德鲁克/TPS，并说清外部方法职责。
5. **下一步和风险**：已确认行动照实写；Agent 新增动作写“建议”；未知参数写待确认。

无法在不删除关键不确定性的情况下压缩时，以真实性优先。后台只保留会改变判断的事实、方法边界、唯一 TPS 状态和行动验证。

## 输出前快速审计

- 是否已选择唯一输出状态？
- `ASK_ONE` 是否只有一个问题及其影响？
- `WAIT_EVIDENCE` 是否只有已整理信息和待核验项？
- 前台外部事实是否均为“已证实适用”？
- 用户既有计划是否标 UJ，Agent 新增行动才标 AS？
- 前台是否把“倾向/考虑”升级成“决定/既定/正确”，或把方法诊断升级成优先级证明？
- TPS 是否严格三选一，具体机制是否满足条件？
- `DELIVER` 是否在正文完整呈现，而不是只声称生成文件？
